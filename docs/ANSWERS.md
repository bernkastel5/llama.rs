## 0. Сначала — фактическая поправка: квантизация НЕ обязательна

> «в текущей версии модель при запуске уже квантуется в Q4… сейчас квантуется в
> обязательном порядке, надо бы добавить выбор»

**Этот выбор уже есть, и по умолчанию квантизация выключена.**

* `src/loader.rs:16-25` — `enum LoadQuantization { #[default] None, Q4K, Q4KM }`.
  Дефолт — `None`.
* `src/main.rs:21` — `quantization: LoadQuantization::None`.
* `src/bin/llama-bench.rs:23` — то же самое.
* `README.md:79` — `-q, --quantize MODE  none, q4k, or q4km (default: none)`.

И главное — `maybe_quantize` (`src/loader.rs:406-419`) выходит сразу, если тип тензора
не `None|F16|BF16`:

```rust
if quantization == LoadQuantization::None
    || tensor.shape.len() != 2
    || !matches!(tensor.quant_type, QuantType::None | QuantType::F16 | QuantType::BF16)
{
    return Ok(tensor);   // уже квантованный тензор возвращается как есть
}
```

То есть **уже квантованный GGUF (Q4_K/Q6_K/Q8_0/…) никогда не переквантуется**, даже
если явно передать `-q q4km`. README это фиксирует прямым текстом (`README.md:14`):
«existing quantized GGUF tensors are used directly and are never requantized».

Вывод: **работа, которую вы хотели заказать, уже сделана.** Заказывать её повторно —
классическое перепроизводство. Если у вас на практике модель всё же квантуется при
старте — значит, вы запускаете с явным `-q q4k`/`-q q4km`, либо грузите SafeTensors
(F32/F16/BF16), где без квантизации просто нет квантованных весов. Пришлите строку
запуска — разберу конкретный случай.

Единственное, что здесь реально стоит сделать (дёшево, из §2.6j плана): load-time
квантизация идёт через `tensor.to_vec_f32()` на **весь** тензор (`src/loader.rs:423`) —
это пик ОЗУ и время старта. Для 3 ГБ ОЗУ и `lm_head` 151936×896 критично. Лечится
построчной потоковой квантизацией. Но это про **загрузку**, а не про скорость генерации.

## 1. Что нового в моём предложении по квантизации

Ключ к путанице: **это два разных места, где встречается слово «квантизация».**

| | Что квантуется | Когда | Уже есть? |
|---|---|---|---|
| **Квантизация весов** (ваша) | матрицы весов модели | один раз при загрузке | **да**, `LoadQuantization`, и выбор есть |
| **Квантизация активаций** (моя) | вектор входа `x` в matvec | на каждом matvec, ~168 раз за токен | **нет** |

Сейчас, даже когда веса лежат в Q4_K, **входной вектор остаётся f32**, и ядро считает
«int4 × f32». Смотрим `src/backend.rs:72` — сигнатура прямо это фиксирует:

```rust
fn matvec(&self, weight: &QuantTensor, input: &[f32], output: &mut [f32]) -> Result<()>;
//                                     ^^^^^^^^^^^^^ активация всегда f32
```

И горячий цикл `dot_q4k` (`src/simd.rs:170-197`) распаковывает вес обратно в float:

```rust
qdot = _mm256_fmadd_ps(_mm256_cvtepi32_ps(codes), values, qdot);  // int4 -> f32 -> FMA
...
sum += d * scale as f32 * hsum(qdot) - dmin * min as f32 * hsum(xsum);  // hsum 8 раз на блок
```

Три потери в этих строках:
1. `_mm256_cvtepi32_ps` — веса разжимаются обратно в f32, вся выгода компактности теряется в ALU.
2. **8 значений за итерацию** (дорожки f32) вместо 32 (дорожки int8).
3. `hsum` **8 раз на блок** из 256 значений — горизонтальная редукция это ~5 инструкций с зависимостью по данным.

llama.cpp вместо этого квантует `x` в Q8_K **один раз на весь matvec** (не на строку!) и
считает `_mm256_maddubs_epi16` в int8 — 32 значения за итерацию, одна редукция на строку.

Измерено (`bench/c/q4k.c`, стоимость квантизации активаций включена в замер):

| форма | сейчас (int4×f32) | предлагается (int4×int8) | |
|---|---|---|---|
| 896×4864 (down_proj) | 1.356 мс | 0.240 мс | **5.66×** |
| 4864×1024 (gate/up) | 1.402 мс | 0.584 мс | **2.40×** |
| 151936×896 (lm_head) | 4.775 мс | 1.199 мс | **3.98×** |
| 200000×1024 (вне кэша) | 52.07 мс | 17.57 мс | **2.96×** |

**Это не меняет формат хранения весов и не трогает загрузку.** Веса как лежали в Q4_K,
так и лежат; меняется только арифметика внутри `dot_*`. Ваш выбор «квантовать или нет»
остаётся ровно таким же.

Побочный ответ на §2.6: пункты оттуда (F16/BF16-ядра, SIMD RMSNorm, таблица RoPE,
`select_nth_unstable`, `VecDeque`) к формату весов отношения не имеют вообще — это
независимые мелкие потери в горячем пути.

## 2. Шаг 2 (воркеры и барьер) — не реализовано, делаем

Проверка: `grep -rn "spin\|Barrier\|persistent" src/*.rs` — ни одного совпадения
(единственное упоминание «persistent» — комментарий в `src/quant.rs:286`).

Текущее состояние (`src/backend.rs:151-155`):

```rust
self.inner.pool.install(|| {
    output.par_iter_mut().enumerate().for_each(|(row, out)| {
        *out = dot_row_for_kernel(kind, weight.row_data(row), weight.quant_type, input)
    });
});
```

`install` + `par_iter_mut` — это fork-join на **каждый matvec**: 24 слоя × 7 проекций ≈
**168 барьеров на токен**. Измерено (`bench/c/barrier.c`, `bench/c/spin.c`):

| | на раунд | на токен |
|---|---|---|
| fork-join (как сейчас) | 50.03 мкс | **8.40 мс** |
| atomic spin-барьер | 0.11 мкс | **0.018 мс** |

Разница **455×**. При целевых ~18 мс/токен нынешние 8.4 мс — почти половина бюджета,
потраченная на синхронизацию, а не на счёт.

Заодно замечу: `dot_row_for_kernel` диспатчит по `KernelKind` **на каждой строке** —
ветвление внутри самого горячего цикла. Выносится наверх бесплатно.

## 3. Шаг 3 (векторизация attention) — не реализовано, делаем

`src/model.rs:214-218` — Q·Kᵀ обычным итератором, без единой SIMD-инструкции:

```rust
for (past_pos, score) in scores.iter_mut().enumerate() {
    *score = q_head.iter().zip(key).map(|(q, k)| q * k).sum::<f32>() * attention_scale;
}
```

`src/model.rs:224` — взвешенная сумма V такая же скалярная. Плюс цикл
`for head in 0..num_heads` (`src/model.rs:208`) идёт **последовательно** — головы не
распараллелены вообще, хотя это идеально независимая работа.

Измерено (`bench/c/attn.c`, 24 слоя × 14 голов, GQA 14→2, hd=64):

| ctx | сейчас | AVX2 |
|---|---|---|
| 256 | 3.174 мс | 0.281 (**11.3×**) |
| 1024 | 14.145 мс | 1.270 (**11.1×**) |
| 4096 | 53.737 мс | 11.608 (**4.6×**) |

При вашем дефолтном `--context 4096` (`src/main.rs:22`) это самая большая единичная
потеря в длинных диалогах.

## 4. Шаг 4 (батч-GEMM prefill) — не реализовано, делаем

`src/architecture.rs:60-75` — дефолтный `prefill` буквально гоняет токены по одному:

```rust
for (index, &token) in tokens.iter().enumerate() {
    ...
    self.forward_token(token, start_pos + index, kv_cache, buffers, mode)?;
}
```

Никто этот дефолт не переопределяет. Значит, на промпте из N токенов веса читаются из
памяти **N раз** вместо одного. Измерено (`bench/c/gemm.c`, 4864×1024):

| N | по одному | батч | |
|---|---|---|---|
| 4 | 0.316 мс/ток | 0.203 | **1.56×** |
| 16 | 0.302 | 0.156 | **1.94×** |
| 32 | 0.340 | 0.153 | **2.23×** |

Это напрямую бьёт по «времени до первого токена» — самой заметной для человека части
задержки. README сам называет это следующим крупным шагом.

## 5. Шаг 5 (f16 KV-кэш) — применим ли при квантованных моделях?

**Да, полностью применим — это ортогонально формату весов.**

KV-кэш хранит не веса, а **вычисленные во время работы** K и V. Сейчас он f32 всегда,
независимо от квантизации модели (`src/cache.rs:6-7`):

```rust
pub k_cache: Vec<Vec<f32>>,
pub v_cache: Vec<Vec<f32>>,
```

Даже если вся модель в Q4_K, кэш остаётся f32. При `--context 4096` × 24 слоя × 2 kv-головы
× 64 = это десятки мегабайт, которые перечитываются на **каждом** токене. f16 режет их вдвое.

Измерено (`bench/c/attn.c`):

| ctx | AVX2 f32-KV | AVX2 f16-KV | |
|---|---|---|---|
| 256 | 0.281 мс | 0.348 | 0.81× (**хуже**) |
| 1024 | 1.270 | 1.338 | 0.95× (хуже) |
| 4096 | 11.608 | **5.795** | **2.00×** |

Отсюда честный вывод: **на коротком контексте f16-KV вредит** (конверсия стоит дороже
экономии, пока всё влезает в кэш). Выигрыш появляется только с ctx≳2k, когда упираемся
в память. Поэтому шаг 5 — за флагом и с автовключением по порогу контекста, и делать
его надо **после** шага 3, иначе нечего измерять.

## 6. Ваш метод тестирования и бережливое производство

> «беру обновлённые файлы, запускаю у себя, смотрю время ответа. Тенденции
> приоритетнее точных оценок»

**Приоритет тенденций над точными оценками — это правильно и полностью соответствует
lean.** В lean контрольная карта важнее единичного замера; вы интуитивно делаете именно
это. Отсутствие llama.cpp под рукой тоже не проблема: цель «≥80% от llama.cpp» — внешний
ориентир, а управлять надо по своей траектории.

Но в текущем виде метод даёт **три систематические ошибки измерения** (в lean это
«загрязнённая контрольная карта» — хуже, чем её отсутствие, потому что порождает
уверенные неверные решения):

1. **Замер по интерактивному ответу зависит от длины ответа.** `src/main.rs:132` вызывает
   `generate_with_metrics`, а сколько токенов сгенерится — решает модель (по EOS).
   Сэмплинг стохастический (`temperature 0.7`, `top_p 0.9`, `top_k 40` — `src/engine.rs`).
   На один и тот же промпт вы получите то 40, то 120 токенов. «Общее время ответа» тогда
   меряет **длину ответа**, а не скорость. Оптимизация, ускорившая код на 20%, легко
   утонет в этом шуме.

2. **Prefill и decode смешиваются в одно число.** Это разные режимы с разными узкими
   местами: prefill — compute-bound (шаг 4), decode — memory-bound (шаги 1–3). Шаг 4
   может дать 2× на prefill и **ноль** на decode. По суммарному времени вы увидите
   размытое «ну, чуть быстрее» и не поймёте, сработало или нет.

3. **Нет истории.** Сравнение «на глаз с прошлым разом» теряет мелкие регрессии. Шесть
   шагов по −3% незаметны поодиночке и съедают 17% суммарно.

Хорошая новость: **инструмент уже в репозитории, просто не используется.**
`src/bin/llama-bench.rs` уже делает всё правильно — фиксированное число токенов,
argmax вместо сэмплинга (`benchmark_tokens`, `src/engine.rs:195+` — детерминированно,
без токенизации), прогрев (`:113-115`), **медиана** по раундам (`:121-127`), `--json`.

### Альтернатива: контрольная карта `llama-track`

Обёртка вокруг `llama-bench`, которая добавляет недостающее — историю и дельты.

```
cargo run --release --bin llama-track -- -m model/qwen-0.5b -p 128 -n 32 -r 5 --note "шаг 2: spin-барьер"
```

Печатает:

```
  decode: 33.10 tok/s  (30.211 мс/токен)
  к прошлому запуску: +16.1%
  к baseline:         +182.9%  (было 11.70 tok/s)
  история: bench/history.csv (3 записей)
```

Что это чинит:
* фиксированные `-p 128 -n 32` → длина ответа больше не влияет;
* argmax вместо сэмплинга → детерминированно, разброс от температуры исчезает;
* prefill и decode разделены → видно, какой шаг что ускорил;
* медиана из 5 раундов + прогрев → устойчиво к фоновой нагрузке ноутбука;
* `bench/history.csv` с хешем коммита и заметкой → **та самая контрольная карта**;
  тренд виден сразу, регрессия ловится в тот же день.

Про **мс/токен** отдельно: в CSV есть колонка `decode_ms_per_token`. Ваше «чем меньше
время, тем лучше» — это она. tok/s растёт нелинейно и на глаз обманывает (с 10 до 11
tok/s и с 50 до 55 — оба «+10%», но первое экономит 9 мс, второе 1.8 мс). Милисекунды
на токен складываются линейно и напрямую сопоставимы с бюджетами из плана
(«−8.4 мс/токен» от шага 2 — сразу видно в этой колонке).

**Ваш интерактивный прогон стоит сохранить** — как приёмочную проверку («ответ
осмысленный, ничего не сломалось»). Но решение «стало быстрее или нет» принимать по
`llama-track`. Разделение приёмки и измерения — это стандартизованная работа: два разных
вопроса, два разных инструмента.

## 7. Совместимость с концепцией и архитектурой

| Требование | Как соблюдается |
|---|---|
| **CPU-only, слабые ноутбуки** | Все шаги — про снижение работы на токен и трафика памяти. f16-KV вдвое режет ОЗУ; потоковая квантизация убирает пик при загрузке. AVX-512 отвергнут — на слабых машинах он даёт троттлинг. |
| **Разные форматы** | Ни один шаг не меняет форматы хранения. Шаг 1 добавляет квантизацию **активаций**; веса читаются как читались. Выбор «квантовать / брать как есть» не затрагивается. |
| **Разные архитектуры** | Шаги 1–6 — внутри ядер и планировщика, ниже уровня архитектуры. `CausalModel` и `KernelBackend` остаются. Шаг 4 переопределяет дефолтный `prefill` — новые архитектуры получают ускорение бесплатно. |
| **Разные виды взаимодействия** | Шаг 4 бьёт по «времени до первого токена» (чат), шаги 1–3 — по потоковой генерации. Батчинг из шага 4 — фундамент для нескольких параллельных запросов. |
| **Lean** | Одно изменение = один коммит = один замер. Отказ от AVX-512 по измерению — устранение ненужной работы. Отказ от «выбора квантизации» — устранение перепроизводства (уже сделано). Тесты паритета до оптимизации — jidoka. |

**Инвариант, который нельзя нарушать:** абстракция снаружи горячего цикла,
мономорфизация внутри. Trait-объект на уровне слоя бесплатен. Диспатч на уровне строки
матрицы (как сейчас `dot_row_for_kernel`) съедает производительность. Любое новое
обобщение, добавляющее ветвление внутрь цикла по строкам, сделано неправильно.
